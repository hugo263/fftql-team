# 部署与回滚操作说明（未执行，需另行授权）

## 发布范围

只允许 `server.js` 的模块路由挂载、`public/admin.html` 的导航入口和新增 `xhs/` 运行文件。不要发布整个隔离副本，不要覆盖 config.json/data、v109 文章静态文件、资讯 v15 或反馈分支。`xhs/preview.cjs`、测试、截图、`.local-xhs/`、本地 data/ 均不能部署。

代码挂载默认关闭：未设置 `XHS_ENABLED=1` 时不加载模块、不创建数据库，后台新入口返回 404。建议批准发布时一起开启，避免保留无效入口。现有管理员登录和权限不变。

## 发布前准备

1. 再次核对线上 server.js/admin.html 与 `baseline.json`，并核对届时 Git 分支/反馈任务状态。两文件若有新变化，重新合并 9 行路由挂载和一个导航链接；禁止整份替换或 force 覆盖。现有基线哈希在 manifest。
2. 确认生产 Node 24 支持 `node:sqlite`，固定版本；当前只读检查 v24.18.1，本地 v24.17.0 验证通过。
3. 明确批准服务身份/目录权限。主站当前为 root；不要为本功能默默增加长期 root worker。`xhs-worker.service.example` 的身份是未填写占位符，必须选已审查的服务身份与最小目录访问，新增账号/权限需用户单独授权。此模板不能直接启动。
4. 创建持久目录 `/var/lib/fpl-xhs`（0700）并限制到上述身份；放在 release 目录外，与网页服务共享同一目录。数据库不可位于 public/NFS；保留 SQLite WAL/SHM。初始素材限 2 GiB，另外准备独立备份容量。
5. 按 env.example 建立 `/etc/fpl-xhs.env`，权限 0600，初始 `XHS_ENABLED=0`、`XHS_ALLOW_MOCK=0`、明确 XHS_ORIGIN。主站也必须读同一配置（systemd drop-in EnvironmentFile），否则 worker 与 API 可能不同目录。配置不含真实账号凭据。
6. 先部署到私有暂存目录检查代码和文件清单；测试与源码补丁 hash 对齐；备份当前两个集成文件和已有 xhs 代码（如有）。通过授权后应用精确差异，不推送未经审查文件。

## 启用与验证

完成上述授权、代码和身份确认后，切换 XHS_ENABLED=1，按现有维护窗口重启**主站服务**及新增的 xhs-worker。不重启资讯、不修改其 PostgreSQL/采集/反馈模块，不改其他 vhost 或共用端口。

worker 是独立 systemd 进程，自动恢复与内存限制见模板。首次启动创建向后兼容的新 SQLite 表，不更改主站旧 data。没有启动任何发布浏览器或真实账号适配器；manual 是正式默认通道。

检查未登录页面重定向，API/素材 401，跨源写 403；管理员上传、预览、版本确认、日期时区、取消均可操作。用**合成账号**先模拟验收，若在暂存开启 mock，要明确独立测试数据并在正式前关闭。不得把 mock 的“已发布”当成真实笔记证据。

观察 systemd active/Restart 计数和数据库任务状态，不打印请求体、Cookie 或环境文件。记录任务数量、最老 due_at、连续失败/unknown 数量、磁盘余量。首版只有后台状态/审计与进程通用错误日志，没有另建告警服务或邮件发送；如需主动提醒另行确定渠道。

## 备份

低流量首版使用短维护窗口：停止 worker、暂停 API 写入后，运行：

```sh
node xhs/backup.cjs --writers-stopped /var/lib/fpl-xhs /approved/backup/new-unique-directory
```

脚本使用 SQLite backup API、复制全部私有素材，不输出数据内容；目标必须不存在。SQLite 快照和素材应同批保存。不得只复制运行中的 xhs.sqlite 而漏 WAL，也不能把代码 tar 当作数据库备份。脚本开关是操作人对停止写入的声明，不会替你停止生产进程。恢复前须在隔离目录验证备份可读、素材 hash 完整。

## 代码回滚

1. 停止新增 worker，关闭 API 的 XHS_ENABLED；先保留数据与审计，并导出/记录所有“已交付/待核实/取消待确认”任务清单。
2. 对比已发布后的文件 hash；只有仍匹配本次内容才能恢复两个集成文件，否则手工逆向合并本次片段，保留并发改动。按同样原则恢复 xhs 运行文件。
3. 重启主站验证既有后台与前台。无需切换资讯 release 或回滚 PostgreSQL。
4. **代码回滚不会取消平台上已接受的排期**。对真实通道（未来接入）逐项核实平台并取消；未确认前不能告诉用户已经完全取消。当前首版没有真实平台提交。
5. 保留 SQLite、素材和审计，不删除用户内容。若仅回滚代码，保持模块/worker 关闭，等兼容版本上线后再恢复读取。

## 数据恢复

优先只回滚代码，避免恢复过时任务快照导致重复提交。必须恢复备份时，先停止 API/worker；把当前目录完整另存后，把数据库和素材一起恢复至新私有目录。随后在不启动 worker 的情况下执行：

```sh
node xhs/quarantine-after-restore.cjs --writers-stopped /approved/restored/data-directory
```

它将所有非终态任务标为待核实、保守视为可能已交付、清除旧租约并停止自动查询。恢复后若有人在备份之后取消/发布/改期，必须人工根据平台和当前审计合并；不能直接重放旧 queued 任务。确认完毕后再重新批准未交付的新版本；平台已交付的先核实取消。任何恢复操作本轮均未执行。
